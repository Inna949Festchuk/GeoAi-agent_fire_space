## 📋 Что делает этот скилл (кратко)

**`fire_monitor_validation_pipeline`** — это автономный пайплайн валидации системы «Стрела», который:

| Этап | Что делает | Результат |
|---|---|---|
| **1. Сбор данных** | Рослесхоз (tochno.st), MCD64A1 (NASA, CMR + LP DAAC), исторические детекции VIIRS — вручную из FIRMS Archive | Ground Truth + данные «Стрелы» по региону |
| **2. Выравнивание** | Репроецирует всё в WGS84 / EPSG:3576 (равновеликая), геодезические буферы 500 м | Единая система координат |
| **3. Дедупликация** | Сливает сырые пер-орбитовые детекции в уникальные очаги (≤500 м + ≤±3 дня) | Очаги со статистикой (cluster_size, first_at, last_at, FRP) |
| **4. Детекция** | Сравнивает очаги «Стрелы» с реестром пожаров (буфер 500 м, период активности ±3 дня) | Precision / Recall / F1 |
| **5. Гари** | Сравнивает полигоны гарей (Sentinel-2 dNBR) с MCD64A1 (±20 дней, буфер 1 км) | IoU, F1, корреляция площадей, лаг |
| **6. Отчёт** | Markdown-отчёт + Folium-карта + CSV метрик + слой «Валидация» на карте приложения | Артефакты для стейкхолдеров |

**Суть:** данные подготавливаются один раз (этап 1), дальше валидация выполняется встроенным инструментом `run_validation` (движок `backend/geo_processing/validation/`) — из AI-чата приложения, через REST или MCP. Регион и период на вход → инструмент добирает недостающее (GT, MCD64A1), дедуплицирует детекции в очаги, считает метрики → готовый отчёт с цифрами и картой.

## 🔁 Дедупликация детекций в уникальные очаги (с 2026-10-23)

Сырые VIIRS/MODIS детекции — это пер-орбитовые точки: один горящий участок
переоткрывается на каждом пролёте (~2 пролёта/день). Для июля 2024 в одном
регионе это 335 075 точек при 1 534 зарегистрированных пожарах — прямое
сравнение даёт Precision ≈ 0,3%, что артефакт гранулярности, а не ошибка
детекции.

Движок **дедуплицирует** детекции в **уникальные очаги**
(`deduplicate_detections()` в `backend/geo_processing/validation/metrics.py`):

- правило слияния — **connected components**: две детекции в одном очаге,
  если они в ≤ `VAL_DEDUPE_DISTANCE_M` (500 м) друг от друга **и** не дальше
  `VAL_DEDUPE_WINDOW_DAYS` (3 дня) по времени;
- представитель очага — самая ранняя детекция;
- у очага статистика: `cluster_size`, `first_at`, `last_at`, `days_active`,
  `frp_max`, `frp_mean`.

Дедупликация **включена по умолчанию** (`VAL_DEDUPE=1`) и действует на
метрики P/R/F1 и на все карты (Folium-слой «Стрела (уникальные очаги)»
с попапом «очаг: N детекций …», слой «Валидация» на карте приложения).
Выключить: параметр `dedupe: false` в `run_validation` (чат/REST/MCP)
или `VAL_DEDUPE=0` в `.env`.

Итог по июлю 2024: 335 075 сырых детекций → **6 860 уникальных очагов**;
прогон ~2 мин (vs ~20 мин без дедупа), Folium-карта ~19 МБ (vs 374 МБ).

## ⏱ Сопоставление по периоду активности очага (с 2026-10-23)

GT-пожар сопоставляется с очагом не по одной «первой» детекции, а по
**периоду активности** `[first_at, last_at]`:

- дата начала пожара из реестра попадает внутрь периода → совпадение
  (dt = 0) — облака могли скрывать старт, VIIRS увидел пожар позже;
- дата до `first_at` или после `last_at` → dt = расстояние до края периода,
  совпадение, если dt ≤ 3 дней;
- без дедупликации (сырые точки) — старое правило
  `|detected_at − fire_start| ≤ 3 дн.`

Плюс геодезический буфер 500 м вокруг точки пожара (не градусы!) и жадная
1:1-привязка «очаг ↔ пожар».

## 📦 Исторические детекции: FIRMS Archive

FIRMS API (`/api/area/csv/`) отдаёт только **NRT-данные за 1–5 дней**
(историческая дата → HTTP 400 «Invalid day range»). Для исторических периодов
(например, июль 2024) детекции заказывают вручную:

1. [FIRMS Archive Download](https://firms.modaps.eosdis.nasa.gov/download/)
   → регион (polygon/bbox) + период + VIIRS (NOAA-20/21) и/или MODIS;
   авторизация — Earthdata Login (или email-код). Придёт zip с JSON.
2. Разархивировать и положить в `fire-monitor/data/strela/`
   (файл вида `fire_archive_J2V-C2_XXXXXX.json`).
3. Конвертировать JSON в `fire-monitor/data/strela/viirs_detections.geojson`
   (Point-фичи с properties: `detected_at` ISO-время, `frp`, `confidence`,
   `source`, `satellite`, `brightness`, `daynight`).
4. Всё — движок подхватит файл автоматически
   (`source='auto'`: файл приоритетнее БД).

Итог по июлю 2024 (Иркутская область): 335 618 точек VIIRS NOAA-21
(все за 01–31.07.2024).

## 🗺️ Шаг 4. Определи тайлы для твоего региона

Данные MCD64A1 разбиты на **синусоидальные тайлы** (36×18, каждый ~1200×1200 км).

### Для Иркутской области / Якутии:

| Регион | Тайлы (примерно) |
|---|---|
| **Иркутская область** (97–119E, 51–60N) | `h21–h26 × v02–v04` — точный список выдаёт скрипт/CMR; г. Иркутск = `h24v03` |
| **Якутия (юг)** (Якутск) | `h23v02`, `h24v02` |
| **Московский регион** (Москва) | `h20v03` |

> ⚠️ Номера тайлов НЕ считаются по «наивной» формуле h=(λ+180)/10 — проверено по CMR
> (июль 2024): Москва=h20v03, Калининград=h19v03, Иркутск=h24v03. Не угадывайте тайлы —
> используйте программу ниже или `downnasagov.py` (ищет сами через CMR).

### Программа для точного определения тайла:

```python
from pyproj import Transformer
import math

def get_modis_tile(lat: float, lon: float) -> str:
    """Возвращает тайл синусоидальной сетки MODIS для координат."""
    # Переводим в синусоидальную проекцию
    transformer = Transformer.from_crs("EPSG:4326", "ESRI:54008", always_xy=True)
    x, y = transformer.transform(lon, lat)
    
    R = 6371007.2  # радиус Земли в синусоидальной проекции MODIS
    tile_size = 1111950.5197  # размер тайла в метрах
    
    h = int((x + 20015109.354) / tile_size)
    v = int((10007554.677 - y) / tile_size)
    
    return f"h{h:02d}v{v:02d}"

# Пример: центр Иркутской области (проверено по CMR, июль 2024)
print(get_modis_tile(52.3, 104.3))  # → h24v03
print(get_modis_tile(56.0, 106.0))  # → h24v03
```

### Визуальная проверка тайлов:
- Карта тайлов: **https://modis-land.gsfc.nasa.gov/pdf/MODIS_sinusoidal_tile_grid.pdf**
- Или интерактивно: **https://ladsweb.modaps.eosdis.nasa.gov/search/map/**

## 📥 Шаг 5. Скачивание данных

### Где теперь лежат файлы (обновлено 2026-10-20)

⚠️ Старые прямые URL вида `ladsweb.../archive/allData/61/MCD64A1/YYYY.DDD/`
**больше не работают (404)**. Данные теперь раздаёт LP DAAC:
`data.lpdaac.earthdatacloud.nasa.gov/lp-prod-protected/MCD64A1.061/<title>/<title>.hdf`,
а точное имя файла (с таймстампом выпуска) отдаёт CMR:
`https://cmr.earthdata.nasa.gov/search/granules.json?short_name=MCD64A1&point=lon,lat&temporal=...`.

Надёжный способ — скрипт (сам ищет тайлы в CMR и скачивает, с кэшем):
```bash
python validation/downnasagov.py --bbox 97,51,119,60 --year 2024 --month 7
```
- токен `EARTHDATA_TOKEN` берётся из `fire-monitor/.env`;
- вывод — `fire-monitor/data/mcd64a1/` (шарится с контейнерами через volume);
- пример имени файла: `MCD64A1.A2024183.h24v03.061.2024251154751.hdf`
  (1 июля 2024 в високосном году = **183-й** день года, а не 182-й).

### Вариант А: curl (ручное скачивание одного файла)

URL берётся из CMR (скрипт `downnasagov.py` делает это автоматически).
Ручная схема: запрос `granules.json?short_name=MCD64A1&point=...&temporal=...`
→ из ответа взять `href` ссылки `data#` (…`.hdf`) →
`curl -L -H "Authorization: Bearer $EARTHDATA_TOKEN" "<href>" -o file.hdf`
(`-L` обязательно: LP DAAC отвечает 303 на presigned CloudFront URL).

### Вариант Б: пакетное скачивание

Готовый скрипт **`validation/downnasagov.py`** (CMR-поиск тайлов + скачивание
с кэшем; работает с хоста, токеном из `fire-monitor/.env`):
```bash
python validation/downnasagov.py --bbox 97,51,119,60 --year 2024 --month 7
```
Старый `MCD64A1Downloader`-код на URL `ladsweb.../archive/allData/...` более
не работает (404) и здесь не дублируется.

### Вариант В: wget

Не нужен: `downnasagov.py` сам проходит редиректы (303 → presigned CloudFront URL).

## 🌐 Способ 2: AppEEARS (без программирования)

Если нужен **конкретный регион** (полигон Иркутской области) без возни с тайлами:

1. Перейди на **https://appeears.earthdatacloud.nasa.gov/**
2. Войди через Earthdata аккаунт
3. **Extraction → Area Extraction**
4. Загрузи полигон региона (GeoJSON) или выбери из списка
5. Выбери продукт: `MCD64A1` (Version 061)
6. Выбери временной диапазон: июль 2024
7. Нажми **Submit** → через несколько минут скачай результат как GeoTIFF (уже в нужной проекции!)

> 💡 **Плюс:** AppEEARS сразу отдаёт GeoTIFF в WGS84/UTM — не нужно репроексить из синусоидальной сетки.
> 
> ⚠️ **Минус:** лимит на размер области (~500×500 км).

## ☁️ Способ 3: Google Earth Engine (без скачивания .hdf)

Если хочешь считать метрики **прямо в облаке**, не скачивая файлы:

```python
import ee
ee.Authenticate()
ee.Initialize()

# Июль 2024, Иркутская область
mcd64a1 = (ee.ImageCollection('MODIS/061/MCD64A1')
           .filterDate('2024-07-01', '2024-07-31')
           .first()
           .select('BurnDate'))

# Область интереса
region = ee.Geometry.Rectangle([97, 51, 119, 60])  # Иркутская обл.

# Экспорт в GeoTIFF
task = ee.batch.Export.image.toDrive(
    image=mcd64a1.clip(region),
    description='MCD64A1_Irkutsk_July2024',
    scale=500,
    region=region,
    crs='EPSG:4326',
    fileFormat='GeoTIFF'
)
task.start()
```

> 💡 В GEE уже есть и датасет Космохака-подобные коллекции, и готовые слои. Удобно для прототипа метрик.

## 🚨 Частые проблемы и решения

| Проблема | Решение |
|---|---|
| `401 Unauthorized` | Токен истёк или не принят Terms of Use. Зайди в веб-интерфейс, прими условия, пересоздай токен |
| `404 Not Found` | Старые ladsweb allData-URLы мертвы (см. «Где теперь лежат файлы»). День года: 1 июля 2024 (високосный) = **183**, не 182 |
| Не знаешь тайл | Используй скрипт `get_modis_tile()` выше или карту тайлов |
| Файл > 100 МБ | Это нормально, MCD64A1 глобальный тайл ~30-60 МБ |
| Нужна коллекция 6, а не 6.1 | Замени в URL `61` на `6` |
